# Design — muse-glimmer-text-recipe

## Approach

Muse Glimmer 30B is the dense, single-GPU sibling of Muse Spark: the same attention (q/k/v/gate projections, scale-less q/k RMSNorm, query × `qk_scale_factor` 3.87, sliding 2048 with rope 500000 on 39 layers and full-context NoPE on 13, sigmoid output gate), the same prompt grammar (`<|start|>role to=X<|message|>`, `to=self` reasoning, ATEM tools), the same softcapped head (`logits × 0.19611… → 20·tanh(x/20)`), the same normed embedding, and a separately published DFlash drafter tapping five target layers. Everything Spark already prepares is imported; what Glimmer does differently is added as an optional parameter defaulting to Spark's behavior; what Spark does not have (dense MLP, TP1 preparation, vision, ModelOpt `config_groups` metadata, the convolution-free drafter) is built from the shared components the other recipes use.

Measured on the checkpoint before this design (HTTP range reads of the safetensors headers and scalars, all 52 layers): `input_scale` equal across q/k/v/gate and across mlp gate/up in every layer; `weight_scale_2` equal across q/k/v and across gate/up in every layer, but attention `gate_proj` differs from q/k/v in every layer (e.g. layer 0: 4.1e-05 vs 2.7e-05). `components/weights.py:788-810` rejects a fused NVFP4 group when either scalar differs, so q/k/v fuse into one projection and the attention gate is a second projection.

Text recipe — new `ignition/recipes/muse_glimmer/`:
- `config.py` — `ModelConfig` validating `muse_glimmer` / `MuseGlimmerForConditionalGeneration`, `text_config` (52 layers, 6656 hidden, 32/2 heads × 128, `layer_types` + `layer_rope_theta` per layer, `sliding_window` 2048, `qk_scale_factor`, `output_multiplier`, `final_logit_softcapping`, `post_norm_eps` 1e-8, `rms_norm_eps` 1e-5, dense `intermediate_size` 19968, `vocab_size` 202048); `attention(layer)` returns Spark's `AttentionGeometry` (imported); `quantization` is the lifted ModelOpt parser's output over the 8 × 52 text projections (q, k, v, attention gate, o, mlp gate/up/down) plus `lm_head` (416 NVFP4 entries; `lm_head` and `model.vision_*` excluded by the checkpoint's `ignore` globs).
- `weights.py` — `DirectWeightLoader` subclass whose `quantization` property returns that mapping, so `load_linear_group` takes its NVFP4 branch: per layer `qkv` (fused q/k/v group), `gate` (attention gate, its own NVFP4 projection), `output` (`o_proj`), `mlp` = `MLPWeights(fused gate/up, down)`, the four centered-norm weights; BF16 `embed_tokens`, `norm`, `lm_head`; `_selected_names` keeps `model.language_model.*` and `lm_head.weight`; the loader asserts `qkv.out_features + gate.out_features == scratch.projected.shape[1]` and documents the row order q, k, v, gate (packed NVFP4 gives no shape signal on a swapped order).
- `model.py` — composes the canonical `MuseGlimmerTextDecoderLayer` (`transformers.models.muse_glimmer`) with the prepared attention and MLP, as `muse_spark/model.py` composes Spark's layer: four `MuseGlimmerTextCenteredRMSNorm`s from checkpoint weights, no residual gates.

- `attention` — Spark's `PreparedAttention` and `AttentionScratch` imported. - `ignition/reference/muse_glimmer.py` — parity reference: the installed `MuseGlimmerForConditionalGeneration` text path with every NVFP4 linear replaced by `ignition/reference/qwen38_quant.Nvfp4Projection` (checkpoint-native decode + calibrated activation quantization), BF16 everything else; `python -m ignition.reference.muse_glimmer SNAPSHOT INPUT_JSON OUTPUT_PT` like Spark's. Built as Spark's layer-streamed reader (one canonical `MuseGlimmerTextDecoderLayer` at a time with its eight linears swapped for `Nvfp4Projection`) rather than the whole `MuseGlimmerForConditionalGeneration`, which would pin a second 23 GB copy beside the prepared decoder; it carries an `Fp8History` cache seam that rounds K/V to E4M3 at the canonical `past_key_values.update` call (after norm and rope, where the prepared rings and pages store them), because FP8 K/V alone measured 3–7 % relative L2 after four layers. The parity bound is calibrated rather than fixed: measured on GPU 0, the prepared residual stream drifts from the FP8-history reference by 3–7 % per layer to ~0.5 relative L2 on the final normed hidden, and the reference alone drifts by the same per-layer curve when only its history precision changes (E4M3 → BF16: [0.032, 0.052, 0.068, …] against prepared [0.0095, 0.034, 0.053, …]), while softcapped logits stay within 0.08 and top-1 agreement at 99.5 %. So the test runs the reference twice (FP8 and BF16 histories) and asserts prepared ≤ 2 × that rounding distance per layer and on the final hidden, logits ≤ 1e-1 relative L2, top-1 ≥ 0.98 and decode reference-argmax rank < 3 (Spark's reference test checks bitwise repeatability only, so there was no Spark whole-model tolerance to reuse; docs/core-design.md already calls whole-model hidden relative L2 diagnostic); the DFlash block bound is 2e-2.

Quantization metadata — `ignition/preparation/quantization.py`:

Decisions:
- One recipe, not three changes: the operator chose "Everything"; each part still exports on its own (`--no-mtp`, `language_model_only`), so verification can land text first.
- Widen Spark rather than copy: the attention and frontend differences are two flags and one path; a copy would fork the FP8 sliding-cache verification path Spark qualified.
- Separate attention-gate projection: measured `weight_scale_2` forbids the four-way fuse; the two-projection form is the minimum that keeps Spark's one-projection form intact.
- Drafter through `components/dflash2.py` with a projector switch rather than through `mimo_v2/dflash.py`: MiMo's DFlash is recipe-local (its attention/decoder imports), while the shared module already matches the assistant's context path and the round driver tolerates no selector; the only differences are the two missing operator families.
- Vision windows as window-ordered varlen segments (Step precedent), not 2-D kernel windows: the kernel's `window_size` is 1-D, so the earlier MiMo-based reading was wrong; the canonical permutation is the attention pattern, not an implementation detail.
- New Helios image profile rather than widening `PatchMerge`: geometry (token cap vs pixel bounds), resampling filter, patch order, window order and position interpolation all differ.
- Lanczos in Helios: the processor's declared `resample: 1` is LANCZOS; bicubic would change pixel values before the encoder runs.
- Fix `conditioned.rs` in this change: the file is in the blast radius and the default arm is the mechanism that would swallow Glimmer's omission too.
- Sampling defaults carried from Spark; the card gives none.

Risks:
- [FP8 paged decode at head_dim 128 with BF16 queries] → qwen38 dense DFlash2 draft rings already run FP8 E4M3 at `(2048, 8, 128)`; the Spark attention test at `capacity 4096` covers the sliding-cache verification path and is re-run at head 128.
- [Width-16 rounds exceed graph budget / token capacity] → `parallel_speculative_shapes` prunes to the budget; `token_capacity` is set from the measured layout at apply and recorded in the recipe.
- [Helios geometry diverges from `smart_resize` on edge aspect ratios] → unit tests enumerate the HF function's candidate set on a size grid; the parity test compares token counts per image.
- [Window order / reverse index mismatch] → the vision parity test includes a ragged grid (not a multiple of 32 patches) and asserts feature-for-feature equality after un-permutation.
- [History-draft copies at block 16] → `parallel_draft.py:50` sizes `copy_token_ids` at width 7 (mirrored by Helios); Glimmer does not enable copies in this change — recorded below as out-of-scope same-class.
- [Assistant repository access] → it answered 200 unauthenticated during propose; the recipe's `snapshot_download` uses the configured hub cache and token as Gemma's does.

## Bomb-squad findings
