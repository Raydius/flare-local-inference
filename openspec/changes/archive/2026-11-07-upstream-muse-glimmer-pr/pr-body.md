Title: Muse Glimmer 30B NVFP4: single-GPU serving with images, DFlash2 drafting, and a 1,048,576-token context

---

Muse Glimmer 30B is a 52-layer text-and-image model whose published NVFP4 checkpoint (`original-el8/Muse-Glimmer-30B-NVFP4`, revision `b47e1e9f77d9a86e18cda5e318c68c632a7fbe59`) fits one SM120 GPU. This adds the `muse_glimmer_nvfp4` recipe under the alias `muse-glimmer-30b-nvfp4`, serving text and images with the `z-lab/Muse-Glimmer-30B-DFlash2` drafter at speculative width 16 and a declared 1,048,576-token context. Two commits, separable: the recipe merges without the context declaration.

1. *Add the Muse Glimmer 30B NVFP4 single-GPU recipe with images and DFlash2 drafting.* Preparation runs on exactly one GPU. The decoder alternates 39 sliding-window layers (2048 tokens) with 13 full-context layers, reads the checkpoint's NVFP4 W4A4 group-16 projections through the ModelOpt `config_groups` metadata, and keeps FP8 E4M3 KV storage, four concurrent requests, and 4096-token prefill chunks. The drafter is downloaded with the target (revision `b54ffdd11fa9cfe2af370012e5763d492c904128`) and runs through the shared DFlash2 components; its head applies the target's output multiplier and logit softcap. Images are resized to the integer patch grid (factor 28) under 4096 merged tokens closest to their aspect ratio and resampled with antialiased Lanczos; video tokens are rejected. Sampling defaults were read from the model card and declared in the recipe. Shared modules are widened with defaults that keep existing call sites unchanged: the Muse Spark attention gains a projection factory (NVFP4 q/k/v/gate written to disjoint regions of one projection scratch) and an `output_norm` switch; the prepared DFlash2 draft scratch's `block_size` field has no default, so every allocation carries the draft's block size (16 for this drafter); the ModelOpt NVFP4 config parser moves from the Gemma 4 recipe to `ignition/preparation/quantization.py`, where it checks 4-bit group-16 weights as before, and Gemma 4 calls it (it accepts and maps the same configurations, `tests/recipes/test_gemma4.py` unchanged; its errors now name the ModelOpt config rather than Gemma 4); Muse Glimmer checks its 4-bit group-16 input activations itself before calling the parser; checkpoint indexing accepts an index whose `total_size` counts shard file bytes; Helios image preparation gains a `MuseGlimmer` profile.
2. *Declare a 1,048,576-token Muse Glimmer context and count width-16 speculative rounds.* The sliding layers attend over 2048 tokens regardless of position and the full-context layers use the checkpoint's unscaled rotary embedding, so the recipe declares the longer ceiling without rope scaling; plans, page budgets, and the package's `max_sequence_tokens` derive from it. `qualify/speculative_benchmark.py` parsed `flare_speculative_*_total` metric names with a width class of `[1-8]`, so a width-16 drafter produced no shape rows; the class is now `[0-9]+`, pinned by `tests/qualify/test_speculative_benchmark.py`.

Package format: `ImagePreparationKind` gains `MUSE_GLIMMER_IMAGE_PREPARATION = 10` and the `profile` oneof gains `MuseGlimmerImageSettings muse_glimmer = 10` (patch size, merge size, maximum image tokens, normalization constants, image/start/end tokens). The addition is additive: packages exported before this change load and serve unchanged, no field or enum value is removed or renumbered, and an engine without this change refuses a Muse Glimmer package with "missing protobuf image profile". `ignition/preparation/runtime_package_pb2.py` was regenerated with libprotoc 35.1.
