## Decisions

- **Rebase, not merge.** `deploy` is a rebaseable patch stack (FORK.md); a merge would end `--update-refs` and make the next base move harder. Rejected: merging `upstream/main` into `deploy`, which keeps 126 commits in place but forfeits the per-patch branches the console image builds are cut from.
- **Default empty-commit handling in the real rebase.** The probe used `--empty=keep` to count stops; the real run lets git drop commits that become empty, because a fork commit upstream already holds should leave the stack. Mitigated by requiring every dropped commit to be named with a reason in the record commit, unlike the probe where seven were dropped silently by a script bug.
- **rerere enabled, but it records only reviewed resolutions.** The `.git/rr-cache` holds the 2026-11-15 resolutions; it is not seeded from the probe, whose resolutions were blind.
- **Acknowledgments.** Replayed commits keep their historical `Design-Signed-Off-By` trailers with hooks off; only commits this change writes are acknowledged, against `1af4`. Rewriting 125 trailers would certify reviews that never happened. Rejected: hook-on for the whole replay.
- **No Glimmer renumbering and no loader guard.** `helios/proto/runtime_core.proto` is untouched upstream since the base, so 11 stays 11, and the console already binds a cache entry to the image that exported it. Rejected: a defensive decode guard, for the same reason the 2026-11-15 change declined it.
- **FlashInfer decided first.** `uv.lock` gates the CPU gate, so the pin cannot be an open question during the replay. Rejected: pinning upstream's line first and patching later, which would run the CPU gate against a FlashInfer the fork does not ship.

## Risks / Trade-offs

- [Risk] The auto-merged Elephant-1 span code (`5acb610d`, `6d67fd70`) never ran against #289 or `10bc91ad` → Mitigation: read-both-sides rule, the Helios Rust suites, and one served masked-decision request on the existing core in step 9.
- [Risk] Taking upstream's `compilation.py` silently drops a fork copy rule that still matters → Mitigation: the net-zero proof (the pair already leaves the file equal to the base today) plus `tests/preparation/test_aot.py` reproducers kept.
- [Risk] The FlashInfer re-cut fails to build against the pinned torch/CUDA → Mitigation: step 3 runs the cases in the serving image before the stack moves, and a failed branch stops the change before any push.
- [Risk] `uv lock` regeneration drifts beyond the pin → Mitigation: `git diff --numstat` must name only the `flashinfer-python` entries.
- [Risk] Rewritten history pushed over `origin/deploy` → Mitigation: eight backup tags exist, per-ref `--force-with-lease` against each tag, `base/current` last, pushes only after every gate.
- [Risk] The TODO fold loses fork entries → Mitigation: count `docs/TODO.md` entries before and after and report both numbers.
- [Trade-off] The probe's blind resolutions under-count stops (3–5 recorded vs 15 "Could not apply" in an earlier variant), so the real run will stop more often than this plan lists; each extra stop inherits its file's rule rather than reopening the plan.

## Migration Plan

Apply order: step 0 → 3 (FlashInfer, before anything moves) → 4 (rebase) → 5 (checks) → 6 (record) → 7–9 (gates) → 10 (push and records). Nothing is pushed before all gates pass, so rollback is local: `git reset --hard backup/pre-rebase-20261118-deploy` plus `git tag -f base/current 6b68b9b4`, and the patch branches are restored from their tags. `origin` is only rewritten ref-by-ref with a lease against each tag.

## Blind Brief

**Problem.** A production fork of an upstream engine keeps its local work as a linear patch stack: a base tag at an upstream commit, five patch branches above it, and a `deploy` branch that adds model recipes, scheduler attribution, serving flags and tooling on top. Every few days upstream advances and the stack must be lifted to the new tip so the shipped container carries upstream's fixes without losing the fork's work. The fork has done this nine times by hand.

**Root cause and category.** `order-of-operations`: the stack must move as one unit — base tag, patch branches and tip — with conflict resolution that keeps both sides' behaviour, and the evidence that nothing was lost has to be produced by the same move. Two facts make it error-prone: an automatic conflict resolution that quietly keeps one side can drop the other side's behaviour without any failing check, and a commit that no longer applies can be skipped silently so its work disappears from the tip.

**Blast radius.** Roughly 125 commits replayed onto 81 new upstream commits. Overlapping files: the model input-packing module and scheduler speculation code (upstream tightened proposal bounds and work estimation), the server request and runtime paths (upstream added image-input handling), the front-end image profile code (upstream added two new input formats where the fork added its own profile), the Python dependency pin and its lockfile (upstream advanced a third-party pin the fork overrides), a qualification benchmark and its tests, and two documentation trees where both sides add entries.

**Questions.**
1. How would you approach this?
2. What blast radius would you expect?
3. What risks would you guard?
4. What is the optimal implementation — performant, correct, efficient — and what would make this run faster?
